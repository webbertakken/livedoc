# API app

The HTTP + WebSocket layer the live editor calls for document persistence and realtime collab.

- **Workspace:** `apps/api` (`@livedoc/api`).
- **Worker name:** `docs-nu-api`.
- **Mount:** routed from the [router worker](../016-platform/router-app.md) at `/api/*`. The router forwards the request as-is — the api worker sees the full `/api/...` path.

## Why this exists

The first prototype phase ([spec 02](../005-project-roadmap/prototype-scope.md)) ran entirely client-side with `localStorage` persistence. Once realtime collaboration entered scope, server state became necessary: a Durable Object per document holds the in-room participant list, orders and relays ops between connected clients and keeps the collaboration state that must outlive a socket, and D1 owns the durable document snapshot. The live app no longer reads or writes `localStorage` for documents — `apps/live/lib/api-client.ts` is the single boundary.

## Tech

- **Runtime:** Cloudflare Workers.
- **DB:** Cloudflare D1 (binding `DB`). Schema lives in `apps/api/migrations/`; each numbered file is one applied change. Treat the migration log as the source of truth on the schema — features get a migration each, so the count grows.
- **Realtime:** Cloudflare Durable Objects (`DocumentRoom`, binding `DOCUMENT_ROOM`). One instance per document id, identified by the document's UUID via `idFromName`.

## Wire-format types

The DTO shapes the api worker emits + the live editor consumes live in `packages/api-schema` (`@livedoc/api-schema`) — `LiveDoc` (published as `Document`), `TabSummary`, `TabRecord`, `TabSaveRecord`, `Folder`, `ShareLink`, `ServerMessage` / `ClientMessage`, and the room op vocabulary (`RoomOp` / `RoomOutgoing` / `RoomIncoming`). Both apps import them; the api worker also re-exports under historical `XxxDTO` aliases (`apps/api/src/types.ts`) for backward compatibility with its existing call sites.

Defining the wire shapes once means server and client cannot drift — adding a field on one side without updating the other is a typechecker error. **Do not redefine these types inline in `apps/api/` or `apps/live/`**; extend the schema package instead. Per AGENTS.md the reuse-over-duplication rule is non-negotiable.

## Auth

The api resolves the request owner through four credentials, in this order (the `Bearer` scheme is read in any case, followed by spaces or tabs, as RFC 7235 has it); the first one present decides, and one that is present but wrong is refused, never read as a guest (see [Auth + guest access](../014-identity/auth-and-guest-access.md#how-the-api-knows-who-is-calling) and [Public API and API tokens](public-api-and-tokens.md)). Token prefixes are checked first: they are cheap string tests, and a session token never carries one.

1. **API token** — `Authorization: Bearer livedoc_…`. `resolveApiToken` hashes it and looks up a live (non-revoked, non-expired) `api_tokens` row; the owner id is that row's account id, so a token request flows through the same ownership and gate checks as a signed-in one. A bearer with the prefix that does not resolve (unknown, revoked, expired, or cut short) is refused `401 invalid_token`. A token minted **read-only** is refused on every `POST` / `PUT` / `DELETE` with `403 read_only_token`, at one choke point in `index.ts`.
2. **Workbench session** — `Authorization: Bearer lvw_…` ([Workbench embeds](../013-workspace/workbench-embeds.md)). `resolveWorkbenchSession` hashes it and looks up a live `workbench_sessions` row of a live token; an unknown, expired or revoked one is refused `401 invalid_session`, never read as a guest. The owner is the session's owner, `sessionAccountId` and the token stay null (a person's editor, never an administrator or an agent), and `workbenchRefusal` confines it before any route runs, by its scope: a document session answers another document `404`, any route outside `WORKBENCH_ROUTES` `403 workbench_confined`, and an `X-Share-Code`, `X-Owner-Id` or `X-Share-Password` beside it `403 workbench_confined`; a workspace session reaches the Explorer's routes (`WORKSPACE_ROUTES`), never the account's, and only `X-Owner-Id` beside it is refused. A view session's write, or its read of the share-link list, is `403 workbench_read_only`.
3. **Session token** — any other `Authorization: Bearer`: the 15-minute EdDSA JWT better-auth mints at `GET /api/auth/token`. `getAccountSession` (`apps/api/src/auth/session-token.ts`) verifies it in-process against the public keys in `identity_jwks` (issuer and audience the deployment's origin, `exp` / `nbf` with 5 seconds of skew); its `sub` must be an account id (`acct_…`). One that does not verify falls through to the guest header, logged as `[auth] session_token_rejected reason=<code>`, never the token, because the guest path must always serve. With sign-in off (no `BETTER_AUTH_SECRET`) nothing verifies and every request is a guest.
4. **Guest header** — `X-Owner-Id: <participant-id>`, used when no Bearer credential resolved. The participant id is server-minted by `POST /api/guest-id` and persisted in `localStorage` under `livedoc:v2:self-id`. On the owner-scoped segments (`OWNER_SCOPED_SEGMENTS` in `apps/api/src/auth/guest-rest.ts`: `documents`, `folders`, `images`, `files`, `custom-themes`, `custom-stamps`, `shape-libraries`, `participants`, `preferences`, `shared`, `timeline`, `activity`, `favourites`, `tags`, `home`, `search`, `trash`, `placement-defaults`) two guards run before any handler:
   - A header value shaped like an account id (`isAccountIdShape`, `acct_…`) is refused unconditionally with `401 account_id_not_a_guest_credential`: no real client ever sends one, so it can only be a replayed, harvested account id ([Public API and API tokens §4.1](public-api-and-tokens.md#41-an-account-id-in-x-owner-id-is-refused-unconditionally)). The share resolver applies the same refusal.
   - Wherever sign-in is on (`guestSignatureEnforced`: the host has a guest signing key, derived from `BETTER_AUTH_SECRET`), the header must carry its HMAC in `X-Owner-Sig`, or the request gets `401 signature_required`, logged `[auth] guest_signature_refused route=<segment>`. A guest-only host signs nothing and requires nothing ([Public API and API tokens §4](public-api-and-tokens.md#4-x-owner-id-trust-change)).

The request handler computes the resolution once at the top of `fetch`:

```ts
// tokenAuth (livedoc_), workbench (lvw_), then the session token
const sessionAccountId = accountSession?.accountId ?? null;
const accountEmail = accountSession?.emailVerified ? accountSession.email : null;
const resolveOwner = (): string | null =>
  sessionAccountId ?? tokenAuth?.ownerId ?? workbench?.ownerId ?? request.headers.get('X-Owner-Id');
const verifiedAccountId = sessionAccountId ?? tokenAuth?.ownerId ?? workbench?.ownerId ?? null;
```

Every endpoint uses `resolveOwner()` instead of reading the header directly, so adding new endpoints inherits the hybrid behaviour automatically. `verifiedAccountId` (a server-verified account id from any credential, never the header) feeds the team-membership gates; account administration (teams mutations, `/api/tokens`, `/api/oauth`, workbench pairing, `/api/account`, `/api/migrate`) reads `sessionAccountId` alone, so a token can't reach it. A session token verifies on its own for up to 15 minutes, so on those administration segments (`ADMINISTRATION_SEGMENTS` in `apps/api/src/auth/account-gate.ts`) the account must also still exist in `identity_users`; a deleted account's token gets `401 account_not_found`, logged `[auth] account_not_found route=<segment>`. `accountEmail` is only the session token's verified email claim, never a header: it drives team-invite matching ([Teams](../013-workspace/teams.md)).

`BETTER_AUTH_SECRET` is a **worker secret** (`wrangler secret put`, synced from a GitHub repo secret on deploy), not a `[vars]` entry ([Secrets policy](../002-project-scope/secrets-policy.md)). Leaving it unset puts the api in guest-only mode: `/api/auth/*` answers `404`, no session token verifies and no guest id is signed. Useful for local dev and for any host that wants no accounts.

Visitor-edit endpoints (`PUT /api/documents/:id/tabs/:tabId`) still also accept `X-Share-Code` for share-link auth — that header is checked via `canEditDocument()` and is orthogonal to the account-vs-guest choice. A visitor following a share link is a guest who provides a code, regardless of whether they're separately signed in. When the document has a **share password** ([Share password](../013-workspace/share-password.md)), the same `canEditDocument()` / `canReadDocument()` checks also require a matching `X-Share-Password` header, so every share-code read and write is gated, not just the initial resolve. The owner identity short-circuits the password check. The realtime room upgrade carries the password as the `p` query param (browsers can't set headers on a WS upgrade) and refuses to open the room for a non-owner without it.

### Request bodies

A route whose body is required reads it with `readBody`: `400 invalid json` when it does not parse, `400 expected a JSON object` when it parses to anything else. A route whose every field is optional (minting a share link, the share password, a token, a rescope, a form report, the guest migration) reads it with `readOptionalBody` (`routes/context.ts`):

- An absent or empty body, and a JSON value that is not an object (`null`, a string, an array), read as no fields: `{}`.
- A body that does not read to its end (the stream broke off: a client gone mid-upload) is `400 body_unreadable`, logged as `[request] body unreadable`; a body that does not parse (cut short of valid JSON) is `400 invalid json`. Neither is ever `{}`: on these routes `{}` is a choice (no share password, an edit link to every tab), so a broken request must not make it.

No answer leaves a request body unread, whether the route read it or not (`discardUnreadBody`, `unread-body.ts`):

- Every request reaches the api through the router, which streams the body on into the api as it arrives.
- The router's runtime closes that stream the moment the router's answer is sent.
- A body the api never read is then still being streamed, and the router throws `Can't read from request stream
after response has been sent.`: an exception in the router's Issues for a request that succeeded.
- So before it answers, the api reads to its end a body whose declared length is at most 64 KiB (default), which
  ends the stream before the answer; a longer one, or one of no declared length, it cancels.
- A body a route read, or handed on whole (to a Durable Object, say), is left alone.
- A body that cannot be discarded changes nothing about the answer, logged as `[request] body.discard_failed`.
- The editor's `POST /api/guest-id` sends `{}` and the route reads nothing: that is how this was found.

A path segment the api decodes (a template kind, an element kind, a placement default key) that carries a malformed percent-escape (`%`, `%E0%A4%A`) names nothing: it answers as an unknown name does, `404`, never a `500` from the decoder (`decodePathSegment`, `@livedoc/api-schema`).

### Ids

A document, folder or team is created under an id its caller mints (`POST /api/documents`, `/api/folders`, `/api/teams`). The api keys the record by it and builds paths, room names and scopes from it, so it must be a **key id**: letters, digits, `-` and `_`, 1 to `KEY_ID_MAX` (64) characters (`isKeyId`, `@livedoc/api-schema`). Every id the app mints fits (UUIDs, short ids); anything else, a slash, a colon or a space included, is `400 invalid id`, before anything is written. Tag and shape-library ids already hold to the same set; a custom theme keeps its `custom:` prefix.

### Document dates

A document's dates are its `createdAt` (shown as created) and `savedAt` (last
modified, the lists' order), both milliseconds since the epoch, as everywhere
on the wire. A create stamps both with the server's now, unless the body
carries its own: an Offline Mode sync carries the local record's `createdAt`
([Offline Mode](../006-document/offline-mode.md)), and an imported board
carries the board's own created and last-modified dates
([Microsoft Whiteboard import](../020-import-export/whiteboard-import.md)), so
it sits in the Explorer where its age puts it.

- Each given date must be a whole number of milliseconds no earlier than
  `DOCUMENT_DATE_MIN` (1 January 2000, before any document a person could
  bring) and no later than the server's now plus `DOCUMENT_DATE_SKEW_MS`
  (one day, for a device clock that runs ahead), and `createdAt` must not be
  later than `savedAt`.
- A given `createdAt` alone keeps `savedAt` at now (or at `createdAt`, if a
  clock running ahead put that later); a given `savedAt` alone is refused (a
  document is never modified before it is created).
- Seeding the create's tabs leaves `savedAt` as given.
- Anything else is refused whole, 400 `bad_request` "invalid document dates";
  nothing is created.
- Only a genuine create takes them: re-committing an id the caller already
  owns keeps the stored `createdAt`.

### Marking a document used

Making a document is a use of it for whoever makes it: a use day and their latest use, the measures
[Explorer Home](../013-workspace/explorer-home.md#making-a-document)'s Jump Back In reads. The create body's
`markUsed` decides it.

- Absent or `true`: the making counts, at the server's now. A create that carries dates of its own (an imported
  board) still counts on the day it is made.
- `false`: the document is made and filed as ever, and its creation is in the Timeline as ever, but it is no use:
  it joins Jump Back In at its first open or edit. The editor sends it for every document of an import that makes
  more than one in one go; any client that makes many documents at once should too.
- Anything but a boolean is refused whole, 400 `bad_request` "invalid markUsed"; nothing is created.
- A re-commit of an id the caller already owns, and an Offline Mode sync (`X-Document-Conversion: sync`), are
  not makings of a document, so neither is a use, whatever `markUsed` says.
- `POST /api/documents/:id/copy` (a duplicate, or a copy of a shared document) always counts: one document, made
  on purpose.

### Documents in the Trash

Every document read (`getDocument`, `getDocumentMeta`, the lists, Shared with
you, Favourites, the Inbox, the Timeline) sees live documents only, so a door
nobody remembered fails closed with a 404. The doors that owe a person the
deleted state (every `/api/documents/:id/*` route, `/api/share/:code` and its
`image.svg`, the room ticket) ask `missingDocument` on a miss: 410
`document_trashed` when the document is in the Trash and the caller could have
opened it (owner, joined team member, share-code holder), else 404. The room's
WebSocket upgrade refuses a trashed document with a plain 404, whatever the
ticket or code. `POST /api/documents` over a trashed id answers 410 to its
owner and 403 to anyone else. The daily `0 3 * * *` cron purges documents 30
days in the Trash (`purgeExpiredTrash`, at most 2,000 a run, oldest first).
The same run moves live documents with no element on any tab, unsaved for 30
days, into the Trash with `reason: 'empty'` (`trashEmptyDocuments`, at most
2,000 a run; [Empty document clean-up](../013-workspace/empty-document-cleanup.md)).

### Tab save

The whole-tab autosave (`PUT /api/documents/<id>/tabs/<tabId>`, about every 600 ms while someone edits) runs in the
document's room ([Document storage](../006-document/document-storage.md)): one call from the Worker, then the stored
tab, the changesets the editor had not seen and the room's ledger are read in the room, the ledger merged after the
changesets as before, and the body, its order row, its stats, its image references and the outbox key are written in
one transaction, with no D1 round trip on the save's path.
The Timeline's edit event is written to D1 after the answer. A denied save still answers 403.

### Tab size

A tab is stored as one text value in one row of its room's SQLite (`tabs.data`, the tab's JSON without its id and
name), and a Durable Object's SQLite caps a string, a BLOB and a row at **2,000,000 bytes**, as D1 did
([Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/)).
Local `wrangler dev` does not enforce it, so the api enforces it itself:

- `SQLITE_ROW_MAX_BYTES` = 2,000,000. `MAX_TAB_BYTES` = `SQLITE_ROW_MAX_BYTES` less
  `SQLITE_ROW_HEADROOM_BYTES` (8 KiB) = 1,991,808 bytes of UTF-8 JSON. The
  headroom covers the row's other columns (the tab id, a UUID; the name, at
  most 60 characters, so at most 240 bytes; `updated_at`; SQLite's record
  header) many times over, so a tab under the cap always fits its row.
- Both numbers live in `@livedoc/api-schema`, so the editor checks the same
  cap the worker does and the two cannot drift.
- **Every write of a tab's data** is checked against it, at the storage layer
  (`upsertTab`, `seedTabs`, `swapTabData`), so no route can store what the room's SQLite
  would refuse: document create, the tab save, a comment added or deleted
  through the api, and a Q&A board write. A tab over the cap is refused with
  the named 413 (`payload_too_large`) and nothing is written; the worker logs
  `[tab-size] refused` with the write (`create`, `upsertTab`, `seedTabs`,
  `swapTabData`), the tab id, the bytes and the cap. The comment routes list
  413 among their answers in the OpenAPI manifest. The routes
  also check the request up front, so a create never leaves a document
  without its tabs.
- The cap is not raised and the storage format is unchanged; a tab that needs
  more is a separate decision.

## Caching

Every JSON answer is the caller's live state, so it goes out `Cache-Control: no-cache` unless its
route chooses a policy of its own (the OpenAPI document, the public telemetry summary): a browser
may store it but asks the server again before reusing it. Without it a browser may reuse an answer
the server has since changed: Chromium holds a `410` with no explicit expiry indefinitely, so a
share-link visitor who once saw a document deleted would keep seeing it after the owner restored
it. Not `no-store`: the browser's cache drains a stored answer's body, and without it an answer
whose caller never reads the body holds its request open. Images and SVG snapshots set their own
policies.

The public telemetry summary keeps a few minutes in the edge cache. Storing it is best effort: a
put that fails logs `[telemetry] summary cache put failed` and the summary still answers.

## Background work

Work that runs after the answer has gone (`waitUntil`: telemetry rows, Timeline events, team
mail, Timeline backfills) never fails silently, and never fails the request it came from.

- **Every route's background work logs its failure.** The route context's `waitUntil` attaches one
  catch to whatever a handler hands it: `[background] failed route=<route words>` with the error,
  the route named by its words only (`Post.Teams.Invites`), never an id. A handler hands its work
  over as it is; it adds no catch of its own that would hide a failure from that line.
- **Best-effort writes say so.** A server-side telemetry row that fails to land logs
  `[telemetry] server event failed`; the call still resolves, so no caller waits on telemetry.
- **Each daily cron step is isolated.** The `0 3 * * *` run hands every step (each retention
  sweep, the onboarding emails, the token-expiry warnings, the Trash purge, the empty-document
  sweep, image retention, the Workbench sweep) to `waitUntil` on its own, each with its own catch
  and its own log line, so one failed step never skips another. Inside the onboarding emails each
  stage (welcome, activation, week 1, week 2, win-back) is a step too: a failure logs
  `[lifecycle] stage failed stage=<name>`, and the next stage still runs.

## When a request fails

A request that throws, at any step from resolving who is calling to the route's own work, is
answered by the worker, never left to the runtime's bare error page.

- **The database is unavailable: `503 storage_unavailable`** with `Retry-After: 5`, logged as
  `[d1] unavailable route=<route words>` with the error. It is D1 failing on its side, not the
  request: the same call succeeds once D1 recovers, without us changing anything, so the caller
  retries. The failures that are the database's (`isStorageUnavailable`, `request-failure.ts`):
  - D1's own errors, `D1_ERROR: ` and then one of D1's documented messages
    ([Debug D1](https://developers.cloudflare.com/d1/observability/debug-d1/#list-of-d1_errors)): an
    internal error (`Internal error in D1 DB storage caused object to be reset.`, `Internal error
while starting up D1 DB storage ...`), `Network connection lost.`, `Replica disconnected from
primary.`, `Cannot resolve D1 DB due to transient issue on remote node.`, `D1 DB reset because
its code was updated.`, `D1 DB is overloaded. ...` (a queue or a 10-second resource window that
    lifts), and the free plan's daily row read or write limit (lifts at midnight UTC).
  - SQLite running out of memory inside D1, `SQLITE_NOMEM`: during Cloudflare's D1 incident of
    29 October D1's analytics recorded `out of memory: SQLITE_NOMEM` on a one-row `INSERT INTO
events`, a small `DELETE` and the Home read, so it was the database's state, not the query's
    size.
  - D1 answering something other than its JSON, `D1_ERROR: Failed to parse body as JSON`
    (workerd's `d1-api.ts`, `toJson`): D1's service sent an error page.
  - The transport to D1 failing before D1 answers. The binding's `_send` (workerd's `d1-api.ts`,
    without the experimental `d1_binding_jsrpc` flag the api does not set) awaits its fetch outside
    its `try`, so the runtime's own error reaches the worker with no `D1_ERROR: ` prefix:
    `Network connection lost.` or `internal error; reference = <id>`. Either is the platform's, from
    whichever binding it came, and a retry can succeed. A bare `internal error` with no reference is
    not the runtime's shape and stays a 500.
- **Anything else: `500 internal_error`**, logged as `api error route=<route words>` with the
  error, and counted as an `Error·Api·Internal.<Route words>` telemetry row when
  `TELEMETRY_ENABLED` is on. A D1 error that names the query (a constraint, a type, SQL, a missing
  column) is a bug, so it lands here too, and so does every D1 failure that follows from the query
  itself, because retrying it repeats it and the crash report is how we learn which query it was:
  - `D1 DB exceeded its CPU time limit and was reset.`, `D1 DB's isolate exceeded its memory limit
and was reset.` and `D1 DB storage operation exceeded timeout which caused object to be reset.`:
    D1's documentation traces each to a query doing too much (a scan, a load, a large write). When
    a light query is the one killed by a heavy neighbour, the neighbour is still a query of ours
    that must be found, so a 503 that hides it from Server Crashes would be the wrong answer.
  - The size limits (`Exceeded maximum DB size.`, the account's storage limit, a result past the
    maximum response size): a retry fails the same way until we act.
- Neither body echoes the error's text. The route words never carry an id.
- Both log lines, error and stack included, are kept in Workers Logs
  ([Worker logs](../016-platform/worker-logs.md)), so a failure nobody was tailing can still be read.

**Client IP** is the visitor's own address, `CF-Connecting-IP` (`client-ip.ts`), never the router's: the router hands the api the visitor's request over a service binding, headers and all, so every visitor of docs.nu has a bucket of their own (`apps/router/src/index.test.ts` pins it). An IPv6 address keys on its /64 (`clientRateKey`), and the anonymous form and invite-decline limits on a wider range, an IPv4 /24 or IPv6 /56 (`clientNetwork`), each read with one IPv6 parser (`expandIpv6`). The MCP worker's calls carry no visitor address; none of them reaches a per-IP limit (its telemetry carries `INTERNAL_EVENTS_KEY`).

Other reads (a signed-in or guest `GET`, and every `OPTIONS`) are unmetered. The write ceiling sits well above realistic editing traffic (autosave fires once per debounce window, comments are typed by humans) but low enough to stop a bot from spamming document / image creation into D1 + R2 quota exhaustion. The room-ticket mint is exempt because it shares the per-owner budget with the autosave, and a 429 there would cost a team member the whole session's realtime; `/api/events` is exempt so telemetry never competes with a user's real writes.

Before any limiter, a write whose `Content-Length` exceeds the body cap (`MAX_BODY_BYTES`, or `MAX_IMAGE_BYTES` for `/api/images`, `limits.ts`) is refused with `413`.

Self-host: every limiter is optional. When a binding is absent its check short-circuits to "allow", so deployments without the feature still serve. The bindings are a Cloudflare paid-tier capability; the open-source path stays unaffected (per [Open source + distribution](../002-project-scope/open-source-and-business-model.md)).

## Realtime model

The `DocumentRoom` Durable Object (`apps/api/src/document-room/document-room.ts`) is the realtime hub for one document id. Clients connect via the `/ws` endpoint and immediately send a `hello`; the room broadcasts a `presence` snapshot whenever the set changes.

**Hibernation.** The room uses the Workers WebSocket Hibernation API (`state.acceptWebSocket` + class-level `webSocketMessage` / `webSocketClose` / `webSocketError` handlers) rather than in-memory `ws.accept()`, so the runtime can evict an idle room from memory between messages while every client's socket stays open — an open-but-quiet session no longer bills DO duration. All per-session state that matters (the server-assigned ephemeral presence id, the `X-Verified-Role` trust-boundary role, and the `hello` presence including the remembered `tab-focus` tab) survives eviction in each socket's serialized attachment; only the per-session rate-cap window is in-memory and deliberately resets on a wake.

**Access is gated at the upgrade.** Browsers can't set headers on a WebSocket upgrade, so what admits a socket rides its URL, and a URL is logged (edge logs, Logpush, `wrangler tail`). The editor therefore sends only a one-time ticket, `?t=`, minted over REST moments before (above): single-use, document-scoped and a minute long, so a logged one is already spent. The upgrade still accepts the legacy legs an editor from before 2026-10-17 sends, owner id / its signature / share code / share password as `?o=` / `?os=` / `?s=` / `?p=`, and logs `[room-upgrade] legacy leg admitted` (with `leg: owner | share`) each time one admits a socket; once that line has gone quiet, the legacy legs are removed and the ticket is the only way in. The api worker resolves a role there — the ticket's server-resolved role (see `POST /room-ticket` above; consuming a ticket also satisfies the password gate, since the mint already enforced it), else `edit` for the owner (PERSONAL documents only, and never for an account id, which a signed-in owner presents through the ticket instead — a team document's owner id is visible to every teammate, so it is not accepted as a bare `?o=`; team owners ride the ticket), else the link's role for a valid share code for _this_ document, otherwise none — and **refuses the upgrade outright unless a role resolved** (and, for a password-protected non-ticket non-owner, unless the password matches via a constant-time compare). Team membership is ONLY honoured via the ticket: member ids are account ids deliberately visible to teammates, so a bare `?o=` matching a member must not grant edit (a removed member could otherwise keep joining the room). The resolved role is forwarded to the DO as the `X-Verified-Role` header; the DO re-stamps it onto presence in the `hello` handler, ignoring any role the client typed into its own payload, so that header is the trust boundary. Three more headers ride with it, set on every path so a client can never supply them: `X-Verified-Owner` (`1` when the upgrade resolved as the document's owner, else `0`: from the ticket's `owner` bit, or the legacy bare-`?o=` owner leg; a bit, never an id, which the facilitator baton needs so the owner can always take it back), `X-Verified-Tab-Scope` (a tab-scoped link's tab, empty otherwise) and `X-Verified-Share-Code` (the code that admitted a share visitor, empty otherwise). A room ticket carries the scope and the code from the mint. The DO pins them on the session and confines a scoped session to its tab, live and in catch-up ([Tab-scoped share links](../013-workspace/tab-scoped-share-links.md)).

Edits and presence propagate as `op` messages. The room is **not** a stateless relay: it classifies every op, orders the ones that change the document, rewrites a few fields on the way through, keeps a small amount of collaboration state in its own storage, and stores the document's content in its own SQLite, the system of record for document content ([Document storage](../006-document/document-storage.md), [Realtime conflict resolution](../012-collaboration/realtime-conflict-resolution.md), [Collaboration race hardening](../012-collaboration/collab-race-hardening.md)).

### Op classes

Every op kind belongs to exactly one of three lists in `@livedoc/api-schema` (`packages/api-schema/src/room-messages.ts`), and the class decides its ordering, its role gate, and whether a client may send it at all. The room reads `op.kind` to classify; the payload stays `op: unknown` on the wire.

- **Presence** (`PRESENCE_OP_KINDS`): ephemeral, mutate nothing. Relayed unordered (no `seq`), never logged, never replayed, from **any** connected session, so a view-only visitor still shows peers their cursor, selection, laser, walking character and tab, and can answer a poll.
- **Mutation** (`MUTATION_OP_KINDS`): change the document. Relayed **only from a session whose verified role is `edit`**; each gets a monotonic `seq` within the room's `epoch` and a slot in the catch-up log.
- **System** (`SYSTEM_OP_KINDS`): originated only by the api worker through the DO's internal endpoints, stamped `from: 'system'`. Dropped outright when a client sends one, so no peer can forge a revoke or rewrite a Q&A board.

**Access changes end the sessions they affect.** Two api actions narrow who may be in a room without revoking a link: setting a share password, and a member leaving or being removed from a team. For each, the api calls the room's internal `POST /close-sessions` (never reachable from outside, like `/broadcast`) with what to match: `{ match: 'share-code' }` closes every session a share code admitted, and `{ match: 'person', personTag }` closes the sessions carrying that person tag. Matched sockets close with **4005** (`ACCESS_CHANGED_CLOSE`, reason `access-changed`); nothing is broadcast, so no other session learns who left. The connector stops on 4005 and the editor reloads, which runs the ordinary access path again: a password prompt, a refusal page, or (when access remains another way) the editor. The room logs `[room-access] closed` with the match kind and the count.

**A room holds at most 100 connections.** `ROOM_MAX_CONNECTIONS` (`@livedoc/api-schema`, `room-capacity.ts`) bounds what one Durable Object fans each op out to, and its memory: at 100, a busy session's op costs at most 100 sends. The 101st upgrade is answered and closed at once with **4008** (`ROOM_FULL_CLOSE`, reason `room-full`), before it is admitted, so it holds no presence and receives nothing; the close code is the only refusal a browser can read (an HTTP refusal reads as 1006). The room logs `[room] full` with the document and the count. The editor shows the warning "This room is full. Your changes still save, and you'll join live when there's space." once per spell of refusals (`ROOM_FULL_NOTICE`), keeps working on its own (its saves go over REST as ever, and peers see them on their next load or resync), and tries to join again every minute (`ROOM_FULL_RETRY_MS`) and whenever the tab is shown again, without a further warning; a join that gets in ends the spell. The command line's room stream says "This room is full; waiting for a place…" once and tries again at its longest backoff, and counts as rejoined only once a socket has stayed open a second. Every socket counts alike, whatever its role, its tab or what opened it (an editor, a workbench, the command line's room stream): there is no per-tab or per-role share of the 100.

Besides `op`, the room speaks a few non-op frames: `hello`, `sync` and `facilitator` from clients; `presence`, `catchup`, `cursor`, `facilitator`, `selection-released` and `followers` from the room. `followers` (the presence ids following you, [Follow-me viewport](../012-collaboration/follow-me-viewport.md) "Who follows whom") and `selection-released` go to one socket alone. The `follow` op is presence the room keeps and never relays.

### What the room does to a frame

In order, for every inbound frame: a frame over 256 KiB is dropped; a per-session sliding-window rate cap (240 frames per second) drops a flood; an op from a session that hasn't said `hello` is dropped; a system-kind op from a client is dropped; a tab-scoped session may only touch its own tab and never the document's structure (`scopedSenderMayRelay`), nor rename its tab (`scopedRenames`); a non-presence op from a session whose verified role isn't `edit` is dropped; `poll-start` / `poll-end` must come from the baton holder when one is held; a tab-scoped session's op that would change its tab's reach or point its form off the tab is dropped, judged against the stored tab, and its whole-`tab` op goes out under the stored name (`RoomScopedStructure`, [Tab-scoped share links](../013-workspace/tab-scoped-share-links.md#realtime)). Then:

- **Presence ops** relay to every other socket (or, for `avatar-push`, to the one addressed socket).
- **Mutation ops** are rewritten before they go anywhere: `opForTheWire` strips every comment `authorId` (a guest's credential), and `stampCommentAuthor` sets a posted comment's author name and colour to the sending session's presence, whatever the frame claimed. The rewritten op gets the next `seq`, lands in the catch-up log, relays to every other socket, is recorded in the ledger when it is an `el-delta` or `vote`, and the sender receives a `cursor` frame naming the `seq` its own op took, echoing the op frame's `ref` when it carried one (a positive integer), so the sender knows that op is sequenced.
- Every outbound op frame to a tab-scoped session is filtered or redacted for its scope (`opForScope`), live and in catch-up.

On `hello` the room builds the session's presence itself (`helloPresence`): the id is a server-minted per-socket random (never the connector's owner id), the role is the verified one, and every claimed string is length-clamped. It then sends the joiner a `cursor` frame, replays the running poll and its answers, broadcasts presence (each socket gets the roster minus its own entry), and tells the joiner who holds the facilitator baton.

### Ordering and catch-up

Mutations are totally ordered by the single-threaded DO: a monotonic `seq` within an `epoch`. `epoch` and `seq` are persisted in DO storage (`order-state`) and restored on every wake, so hibernation does not strand reconnecting clients ([Resync without reloading the page](../012-collaboration/resync-without-reload.md)). The catch-up log (the last 256 mutations, `OP_LOG_LIMIT`) lives in memory only. On reconnect a client sends `{ kind: 'sync', epoch, lastSeq }`; `resolveCatchup` answers with the ops it missed, or `resync: true` when the gap is behind the log's floor or the epoch is foreign, and the client re-fetches its loaded tabs from D1 in place.

### What the room stores

The document's content, in the room's SQLite ([Document storage](../006-document/document-storage.md#what-the-room-holds)), and in its key-value storage:

- **`order-state`**: `{ epoch, seq }`, written on every mutation.
- **The collaboration ledger** (`RoomLedgerStore`, `room-ledger-store.ts`; entries defined by the pure `collab-ledger.ts` in `@livedoc/document`): for every `el-delta` and `vote` it sequences, the latest state of each answer, idea, checklist tick, comment and the round's dots, one key per element (plus the tab's vote), tagged with the `seq` that set it. An entry that would pass the storage value limit stops growing. The api reads it back to merge a tab save (see the tab `PUT` above).
- **The live poll** (`RoomLivePoll`, `room-live-poll.ts`, key `live-poll`): the running poll and every answer, replayed on `hello`, dropped on `poll-end`.
- **The facilitator baton** (`RoomFacilitator`, `room-facilitator.ts`, key `facilitator`; rules in `facilitator.ts`): who holds it, the token only the holder was sent, and a grace deadline enforced by a DO alarm when the holder's socket goes away ([Facilitator](../012-collaboration/facilitator.md)).

Per-session state (presence id, verified role, owner bit, tab scope, admitting share code, presence) lives in each socket's serialized attachment, so it survives hibernation; only the rate-cap windows and the catch-up log reset on a wake.

The room's other parts each have a module beside `document-room/document-room.ts`: the session attachment and the verified upgrade headers (`room-session.ts`), the role gate on client ops (`room-op-gate.ts`, the [Share roles](../013-workspace/share-roles.md) level ladder), a tab-scoped session's structure check (`room-structure-gate.ts`, `room-scoped-structure.ts`), the worker-only internal endpoints (`room-internal.ts`) and the presence roster each socket is sent (`room-roster.ts`).

### What the room writes to D1

- **The outbox.** The listing's content summary, the Inbox rows, the cards assigned to someone, the placed images and the search text, pushed from the room's alarm ([Document storage](../006-document/document-storage.md#the-outbox)).
- **Q&A board writes.** `POST /api/documents/:id/tabs/:tabId/qa` hands each board action to the room's internal `POST /qa`; `handleQaWrite` runs them one at a time through an in-memory queue and calls `writeQaAction` (`qa-board-write.ts`), which reads the tab row, applies `applyQaAction`, bumps `qaRev` and compare-and-swaps the row. The result goes out as a sequenced `qa` system op.
- **One telemetry row**: the room counts a multiplayer session once (`Document·Used·Multiplayer`, `reportServerEvent`) into the telemetry events table, when `TELEMETRY_ENABLED` is on ([Telemetry + public transparency dashboard](../017-telemetry/telemetry.md)).

Every other document write is a REST call from a client (see the persistence boundary below).

### Internal endpoints

The api worker reaches the DO through its stub (`env.DOCUMENT_ROOM.get(...).fetch(...)`), which never traverses the public edge, so these paths are implicitly internal:

- **`POST /broadcast`** `{ op, ordered? }`: push a system op to every socket (`from: 'system'`), sequenced when `ordered` is true. Used by share-link revoke (`DELETE /api/documents/:id/share/:code`), a tab delete that takes scoped links with it (both `share-revoked`) and a rescope (`share-rescoped`), via `broadcastShareOp` in `room-client.ts`; after relaying either the room closes the sockets that code admitted. Best-effort: a failure is logged (`[room-broadcast]`), never fails the request, since the D1 write is authoritative.
- **`POST /mutation`** `{ op }`: sequence a document change the worker made, as if a peer had sent it. `el-delta`, `changeset` and `tab-meta` are accepted (400 otherwise); the comment endpoints use `el-delta` so a view-role visitor's comment reaches connected editors (`relayElementDelta`), the changeset route uses `changeset` ([Agent changesets](../024-agents/agent-changesets.md#what-the-room-does)), and the tab rename route uses `tab-meta` (`relayTabRename`).
- **`GET /selections?tab=<tabId>&person=<tag>`**: the elements each connected person has selected on a tab (every `select` is recorded in DO storage per session, pruned when the socket goes), each marked `mine` when the session's person tag is the one asked about. The changeset route reads it to find held elements.
- **`PUT /presence`**, **`DELETE /presence`**: an agent's presence entry with its expiry ([Agent presence](../024-agents/agent-presence.md#presence)).
- **`POST /qa`**: one Q&A board write, above.
- **`GET /ledger?tab=<tabId>&epoch=<epoch>`**: the tab's collaboration ledger, or an empty one when `epoch` isn't the room's current epoch (the saver's cursor can't be interpreted then).
- **`POST /purge`** (**Purging a room**): the document was removed for good, so the room closes every socket (`DOCUMENT_TRASHED_CLOSE`, reason `document-purged`), waits for the ledger's queued writes, drops its alarm and deletes all of its storage: the ledger with its comment, idea and answer text, the order state, the poll, the baton, selections and agent entries. The api calls it (`purgeRooms`, `room-purge-client.ts`, 10 rooms at a time, 3 s each, best-effort and logged as `[room-purge]`) after every removal for good: the Trash purge (by hand, emptying the Trash, and the daily cron), Take Offline (`deleteDocument`) and account deletion (`deleteAccount`), each after its D1 batch has landed.

### Conflict model

- **Different elements on one tab merge.** `el` ops apply by id, so concurrent edits to different elements survive on every peer.
- **The same element is last-writer-wins, over the whole element.** Two `el` updates to one element apply in room order and the later one replaces the earlier, whoever held the selection. The concurrent-selection lock ([Live app](../007-editor/live-app.md)) is advisory and client-only (`remoteSelectionsByElement`, built from `select` ops): it makes these collisions rare, and the room does not enforce it. `tab-meta` patches are last-writer-wins per field, and `document-meta` per whole tab list.
- **Multi-writer fields merge.** Answers, ideas, checklist ticks, comments and dots travel as `el-delta` / `vote` deltas that commute, and whole-element or whole-tab ops don't overwrite a receiver's copy of them.
- **Q&A boards are server-owned** and ordered by `qaRev`.

### The persistence boundary

The room holds the document, its ordering and its collaboration state. Tab content reaches the room through `PUT /api/documents/:id/tabs/:tabId`, fired by each editor's debounced autosave with the editor's whole copy of the tab. The room keeps the last save of a tab, with the room ledger and `qaRev` merged in as described on that row. Each editor's copy already folds in the ops it has received, so the last save normally carries everyone's work; an element edit that reached the saver only after its snapshot can be missing from the stored tab until a later save carries it, while live peers still hold it.

A tab `PUT` is not relayed to the room; it is the editor's autosave and nothing else's. Every other writer of tab content (the MCP server, the CLI, an API-token script) writes a [changeset](../024-agents/agent-changesets.md), which the api records in D1 and relays to the room, and which every later editor save re-applies unless that editor has seen it. The comment and Q&A endpoints also tell the room about their writes.

Every tab the api receives (document create, tab save) runs the stored-tab migration (`migrateStoredTab`) before `isValidTab`, as every tab read does, so an element in a former stored shape (for example freehand points before [Stroke points](../006-document/stroke-points.md)) from a browser loaded before a deploy, an API-token script or a Google Drive copy is stored in the current shape rather than refused.

## Data model

The schema starts at `0001_init.sql` and evolves migration-by-migration; the migration files double as commit history of the shape. Today, in broad strokes:

- **`documents`** — id, owner, name, share flag, folder fk, timestamps. The original `data` JSON column was dropped in migration 0006 once tabs moved to their own rows.
- **The content** — tabs, tab order and folders, tab stats, image references, changesets, items and sheets — lives in each document's room, not in D1 ([Document storage](../006-document/document-storage.md#what-the-room-holds)); D1's former content tables stay until every document has moved ([Moving content into rooms](../006-document/document-storage-move.md)). Every route under `/api/documents/:id/` may answer **503 `room_unavailable`** (the room failed or could not take over its earlier state) or **503 `content_moving`** (its content has not moved yet), each with `Retry-After: 5`.
- **`documents.content_summary`** — the listing's view of the content, pushed by the room ([Document storage](../006-document/document-storage.md#the-content-summary)).
- **`document_images`**, **`collab_threads`**, **`collab_actions`**, **`inbox_cards`**, **`content_search`** — the cross-document indexes each room's outbox feeds ([Document storage](../006-document/document-storage.md#the-outbox), [Content search](../013-workspace/content-search.md)).
- **`participants`** — id, name, color. Volatile presence/status state stays on the wire.
- **`share_links`** — code → documentId + role. Multiple links per document are supported; revoking a link is a row delete.
- **`folders`** — id, owner, name, optional self-referential `parent_id`. Documents reference a folder via `documents.folder_id`. Both FKs `ON DELETE SET NULL` so deleting a folder promotes its children. Cycle prevention is enforced in the API layer (D1 can't declaratively).
- **`shared_with`** (migration 0010) — `(owner_id, document_id, role, last_seen)`, primary key on `(owner_id, document_id)`. Tracks which documents a non-owner has accessed via a share link so the Explorer can render a "Shared with you" accordion. FK to `documents` with `ON DELETE CASCADE` so deleting / revoking a document drops every visitor's reference for free.

Document-store hybrid: meta + folder + share state lives in real columns; element content lives in tab `data` JSON. Element-level SQL filtering isn't a use case today, so normalising element rows would buy nothing — and the editor already round-trips JSON for every save.

### Owner-keyed data

This is the one list of columns that hold an owner id (a guest id or an account id), and what the two owner-wide operations do with each: **account deletion** (`deleteAccount`, `DELETE /api/account`) and the **owner migration** (`migrateOwnerId`, `POST /api/migrate`: guest → account at sign-up, and legacy guest → signed guest). Both live in `apps/api/src/db/account.ts`. The owner migration moves its table rows in **one D1 batch** (one round trip, and all or nothing: a failure part-way no longer leaves a half-moved account); no foreign key reads an owner column, so only each table's own order matters, which the batch keeps (the image grant before the documents move, each copy before its delete). The timeline, alias, document-open and shape-library steps follow it. A column holding an owner id is named `owner_id` (`user_id` on `team_members`); `apps/api/src/db/account-owner-columns.test.ts` finds every such column in the migrated schema, fails until it is listed here, and proves each row below against a real SQLite database. Each table here is keyed by owner first; the statements that find rows by document (a document delete's cascades into `favourites`, `document_opens`, `workbench_tickets`, `workbench_sessions` and `workbench_session_rooms`) or by author (`agent_changesets`) seek an index of their own (migrations 0091 and 0099, `apps/api/src/db/lookup-plans.test.ts`), so they never read the whole table.

## One-time setup

Before the first deploy:

1. `pnpm --filter @livedoc/api exec wrangler d1 create livedoc`
2. Copy the printed `database_id` into the `[[d1_databases]]` block in `apps/api/wrangler.toml`. The block is already there with its binding name (`DB`) — only the id changes. What is committed is docs.nu's own database id, so a self-hoster is replacing a real value rather than filling in a blank.
3. `pnpm --filter @livedoc/api run db:migrate:remote` to apply migrations.

After that, GitHub Actions handles deploys via `deploy.yml` (`deploy-api` step). The router's service binding to `docs-nu-api` means the API must deploy before the router.
